> **TL;DR**
> - 公式: `claude --bg` で始めたセッションは、落ちても公式の常駐プロセスが起こし直す
> - 公式: セッションの状態は `claude agents --json` で取れる
> - 自作: 端末で動かして落ちたセッションは公式の一覧から消えるので、会話の記録から拾う
> - 自作: 止まり方と推奨の選択肢を Telegram のボタンで出し、押せば完了まで再開させる
> - 自作: 後から別の作業が同じファイルを触っていたら、古いセッションは再開させない

![上の段が Claude Code の公式機能、下の段が自作](/images/20261019-claude-code-session-watch-telegram/arch.png)

## なぜ作ったか

Raspberry Pi 5 で Claude Code のセッションを何本も長時間回している。止まったら Telegram に「プロセスが消えた、再開が必要」と届く見張りを前から置いていたが、これが毎時届く。開いてみたら 3 件とも、こちらへの質問でターンを終えていただけで、しかも 1〜3 日前のものだった。プロセスの生死しか見ていないので、どう止まったかも、何を押せばいいかも分からない。

作り直す前に、Claude Code の公式機能でどこまで足りるかを調べた（公式ドキュメント code.claude.com/docs/en/、Claude Code 2.1.303）。

## 分担（先に結論）

| やること | 担当 | 中身 |
|---|---|---|
| セッションの状態を取る | 公式 | `claude agents --json` |
| 落ちたセッションを起こし直す | 公式 | `claude --bg` で始めたものだけ。常駐プロセス（supervisor）がやる |
| 端末で動かして落ちたセッションを見つける | 自作 | 公式の一覧に載らないので、会話の記録から拾う |
| どう止まったかを判定する | 自作 | 会話の記録の末尾を読む |
| 後から別の作業が入っていないか調べる | 自作 | `git log --all` |
| スマホに通知して、推奨の選択肢を選ばせる | 自作 | Telegram のボタン |
| 再開する | 自作が公式のコマンドを呼ぶ | `claude --bg --resume` など |
| 再開したら完了まで止まらせない | 自作 | 再開時に渡す指示と、完了の印 |

公式に任せたのは「状態を取る」と「落ちたら起こし直す」の 2 つ。残りは自作で、2 分ごとのタイマーで回る Python のスクリプト 1 本になっている。

## 公式がやること

### 状態の一覧: `claude agents --json`

公式ドキュメントに "the supported way to read session state from outside Claude Code" とある。Pi 5 で 0.33 秒。前の見張りはプロセスの生死を自分で見ていたが、これに乗り換えた。

- 端末で動かしているセッション: `busy` / `idle` / `waiting`
- バックグラウンドセッション: `working` / `blocked` / `done` / `failed` / `stopped`

載るのは "every live session"、つまり生きているものだけ。端末で動かして落ちた対話セッション 4 件は、`--all` を付けても出てこなかった。

### 落ちたら起こし直す: `claude --bg` と supervisor

`claude --bg` で始めたセッションは、公式の常駐プロセス（supervisor）の配下で動く。作業しているプロセスを SIGKILL してみたら、約 12 秒で起こし直して作業を最後までやった。ただし supervisor ごと落とすと `state: failed` のまま、誰も起こさない。

### スマホから見る・答える: Remote Control と Channels

Remote Control（claude.ai やスマホのアプリからセッションを操作する機能）と Channels（Telegram などから話しかける機能。research preview）がある。どちらも、セッションが動いている間だけ使える。Remote Control のプッシュ通知は "there is no per-event configuration" で、どの出来事で通知するかは選べない。claude.ai へのログインが前提で "API keys are not supported"。

## 公式で足りないところ

- 端末で動かしていたセッションが落ちると、公式の一覧から消える。うちは SSH 越しの端末で動かしているので、これがいちばん多い
- supervisor ごと落ちると `failed` のまま残る
- 止まった古いセッションが、もう別の作業に追い越されているかは、誰も見ていない

公式でも状態は取れるし、起こし直しもできる。ただ、管理できることと運用に乗ることは別で、推奨案を見て押すのはどのみちこっち。押す場所は、運用の通知が全部集まっていて毎日開いている Telegram に置いた。ここからが自作の部分。

## 自作 1: どう止まったかを判定する

公式の一覧に載っていれば、その状態を使う。載っていなければ、会話の記録（`~/.claude/projects/<dir>/<sessionId>.jsonl`）の末尾で決める。通知は状態が変わったときだけ 1 回。

| 止まり方 | 根拠 | 推奨 |
|---|---|---|
| 途中で落ちた | 最後が道具の呼び出し・道具の結果・未返答の指示 | 再開 |
| 返事待ち | 最後の発言の末尾が質問 | 選択肢（`claude -p --tools "" --model sonnet` で発言から抜き出す） |
| 完了 | 最後の発言に完了の印 `CSW-DONE:` | 監視をやめる |
| 後続の作業あり | 止まったあと、触ったファイルに別のコミット | 監視をやめる（再開は出さない） |

## 自作 2: 後から別の作業が入っていたら再開させない

例の 3 件が触っていたファイルを見たら、止まったあとに別の作業のコミットが 12 / 8 / 4 件入っていた。続きはもう別のセッションが進めていて、通知どおりに再開を押していたら、古い前提のまま同じファイルを触り直すところだった。

```bash
git log --all --since="<最後の記録の時刻>" -- <そのセッションが Edit/Write したファイル>
```

これで出てきたら再開のボタンを出さない。そのセッション自身の PR が止まったあとで squash マージされた分（件名が同じもの）は除く。最初はファイルの更新時刻で見ていたが、やめた。`git pull` でも変わるし、別の worktree での編集は出てこない（1 件は、更新時刻だと 0 件、コミットだと 4 件）。

記録は大きいもので 742MB あったので、読んだ位置を覚えて差分だけ読む。初回 9.7 秒、2 回目から 0.29 秒。

## 自作 3: Telegram のボタンから再開する

ボタンを押すと、bot が共有ディレクトリにファイルを置き、次の巡回（2 分ごと）がホストで再開する。再開に使うのは公式のコマンドで、どれを使うかを状態で変えた（どれも Pi で試した）。

| 状態 | 自作のスクリプトが呼ぶ公式のコマンド |
|---|---|
| 端末で落ちたセッション / `failed` | `claude --bg --resume <sessionId>`。同じ sessionId のまま supervisor の配下に入る |
| `done` / `stopped` | `claude stop <id>` してから `claude -p --resume <sessionId>`。`--bg --resume` だと 2 回とも別のセッションに分かれた |

端末で落ちたセッションも、一度 `--bg` で再開すれば、以後に落ちたときは公式の supervisor が起こし直す。

## 自作 4: 再開したら完了まで止まらせない

最初は再開の指示に「判断が必要になったら止めて質問を書いて」と入れていた。試したら、質問を 2 つ書いてまた止まった。離席中に使う機能なので、これでは意味がない。

止まってよいのは 2 つだけにした。元の依頼を終えて確かめた（`CSW-DONE: <何で確かめたか>`）か、ログイン・課金のように人間にしかできない操作が要る（`CSW-BLOCKED:`）か。それ以外は推奨案を自分で選ばせる。印なしで止まったら、巡回が自動でもう一度再開する（最大 6 回。同じ止まり方が続いたら打ち切る）。本物の Claude で 3 回通して、3 回とも `CSW-DONE` まで行った。

## 途中で踏んだもの

- 押したその巡回で、起動直後のセッションを「落ちている」と判定して二重に再開した（公式の一覧に載るまで少しかかる）
- Python の文字列の `hash()` は実行ごとに変わるので、巡回をまたぐ比較に使えなかった（sha1 にした）
- subprocess で `claude -p` を呼ぶと stdin を 3 秒待ち、警告を stdout に混ぜて JSON が壊れた（`stdin=subprocess.DEVNULL`）
- バックグラウンドセッションの作業プロセスは、プロセス名が `claude` ではなく版番号の `2.1.303` だった。プロセス名で生死を見ていた判定が「落ちた」と誤った

## 使ったもの

| 項目 | 中身 |
|---|---|
| Claude Code | 2.1.303（公式: `claude agents --json` / `claude --bg` / `claude -p --resume` / `--permission-mode auto`） |
| 選択肢の抜き出し | Claude Sonnet（`claude -p --model sonnet`） |
| ホスト | Raspberry Pi 5、systemd --user のタイマー、Python 3 |
| 通知 | Telegram Bot API（inline keyboard。押したデータには HMAC-SHA256 の署名） |

## 自分の環境で確かめるなら

- 長い作業は `claude --bg` で始め、作業プロセスを kill してから `claude agents --json` で `working` に戻るか見る
- 端末で動かして落ちたセッションの `sessionId` が、`claude agents --json --all` に出るか見る
- 再開の指示に、止まってよい条件と完了の印を書く
- 古いセッションを再開する前に、触ったファイルの `git log --all` を見る
