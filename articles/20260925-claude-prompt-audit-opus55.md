> **TL;DR**
> - `/claude-api prompt-audit` は Claude Code 2.1.282 に同梱された `claude-api` スキルのサブコマンドです。手順書付きの監査で、量が多くてもサブエージェントに分担させれば回せます
> - Raspberry Pi 5 で動かしている自律エージェントに当てたところ、指摘 107 件のうち 63 件を反映し、強調の ★ は 22 → 5、報告前チェックは 13 → 10 項目になりました。5 分とはいきませんでしたが、かなり削れました
> - 引っかかった中身は、古い書き方より**事実のずれ**（存在しないパス・古い設定値・古いモデル名）が多めでした
> - effort の上書きキーが旧 ID のままで、Opus 5.5 は全体設定の `xhigh` で動いていました。effort はエージェント定義では変えられず、効いているかは transcript でしか確かめられません
> - 禁止事項は、外して挙動を比べてから畳んでいます。1 項目だけ、外すと望ましい提案が 3/3 → 0/3 に落ちるものがあったので残しました
> - JSON を本文から切り出していた箇所は `--json-schema` に置き換え済みです（ルートは object 限定）

X で「`/claude-api prompt-audit` と打てば、skills・CLAUDE.md・プロンプトを Opus 5.5 の公式ガイドで書き直してくれる」という投稿が流れてきました。

私は Raspberry Pi 5 で自律エージェントを動かしていて、Claude は Claude Code の CLI（`claude -p`）経由で呼んでいます。ルールファイルやエージェント定義、実行時に渡すプロンプトは数か月かけて積み上げたもので、書いた当時のモデルに合わせた言い回しがたくさん残っています。本当に書き直せるなら使いたい。そう思って、実際に当ててみました。

## まず、エイリアスの実体を測る

監査の対象モデルを決める前に、自分の環境で `opus` が何に解決されるかを見ました。

```bash
for m in opus sonnet; do
  claude -p --model $m --tools "" --output-format json "ok とだけ返して" \
    | python3 -c "import json,sys;print('$m ->', list(json.load(sys.stdin)['modelUsage']))"
done
# opus -> ['claude-opus-5-5']
# sonnet -> ['claude-sonnet-5']
```

ルールには「既定は Opus 5」と書いてありましたが、実体はすでに Opus 5.5 でした。エイリアスで指定していると、モデルが勝手に新しくなり、プロンプトだけが古いまま残ります。監査の対象はこの Opus 5.5 にしました。

コードが Messages API を直接呼んでいないことも確かめました。thinking の無効化・forced `tool_choice`・prefill は Opus 5.5 で 400 になりますが、私の環境では Claude 経路に 0 件でした。API の破壊的変更は当たらないので、監査はプロンプト本文に集中できます。

## prompt-audit の中身

`/claude-api prompt-audit` を打つと、スキルの `shared/prompt-audit.md` を読んでその手順どおりに動きます。

1. 対象範囲と対象モデルを決める（聞き返さず、前提として報告に書く）
2. プロンプトとして効いているものを棚卸しする（system prompt、ツール定義、SKILL.md、CLAUDE.md、リクエストを組み立てるコード）
3. 来歴を見る（`git blame` で「どの事故を防ぐために、どのモデルのときに足したか」）
4. パターン表で照合する（強すぎる口調、API 機能で置き換わった足場、過剰な指定、古いモデルの名残）
5. 報告（`file:line`・根拠・確度）と diff を出す
6. 挙動で検証する

5 分とはいきませんでしたが、手順書はかなり丁寧です。「削除は仮説であって結論ではない」として、消した指示が本当に不要だったかを挙動で確かめるところまで書かれています。「消してはいけないもの」のリストもあり、文脈・理由・今も起きる失敗への禁止事項は残すよう指示されているので、安心して任せられました。

範囲が広かったので、4 つの区画に分けてサブエージェントに監査させ、確度が中以上の指摘だけを反映しました。

| 区画 | 指摘 | 反映 |
|---|---|---|
| CLAUDE.md とルールファイル（6） | 21 | 10 |
| エージェント定義（6）と SKILL.md（10） | 23 | 9 |
| 実行時に `claude -p` へ渡すプロンプト（コード内） | 13 | 4 |
| 参照用のドキュメント（38） | 50 | 40 |

## 出てきたのは事実のずればかり

パターン表にある古いモデル向けの強い口調も直しました。ただ、ずっと多く出てきたのは書いてあることと実物の食い違いで、直した効き目もそちらが大きかったです。

- **一度も読み込まれていなかったルール**: ルールファイルの読み込み条件（`paths:`）が 4 月のリファクタで消えたファイルを指したままで、そのファイルを触るときに読ませたいルールが、それ以来一度もロードされていませんでした
- **「除去済み」の課金 API キー**: ルールには「課金経路は全ルートから除去した」とありましたが、予備として 1 つのルートに残っていました。ログが残っている期間で成功 0 件・失敗 144 件で、課金は発生していないものの、失敗するだけの予備として夜間タスクの全滅に加わっていたわけです
- **書き写した現在地**: スキルが進捗ファイルの「現在地」を書き写していて、本体と食い違っていました。写しは消して、本体だけを正にしています
- **自分に一致して終わらない待機ループ**: `until ! pgrep -f "tidy-imports"` は、実行している bash のコマンド全文にも一致するので、いつまでも終わりません

どれも grep と設定ファイルで実値と照合すれば確かめられるものです。書き方の問題ではないので、モデルが新しくなっても自然には直りません。

口調の書き換えもしました。実行時プロンプトの「必ずツールを使え」「推測で回答しないでください」は、何を根拠にするかと理由を書いた平叙文にしています。要求は変えていません。

## effort の罠

effort（思考量）の件がいちばん効きました。

Opus 5.5 は API の既定 effort が `medium` です（Opus 5 は `high`）。同じ effort でも Opus 5 より多く考える、とガイドに書かれています。私の `~/.claude/settings.json` はこうなっていました。

```json
{
  "effortLevel": "xhigh",
  "modelSettings": {
    "claude-opus-5": { "effortLevel": "high" }
  }
}
```

`modelSettings` のキーは実モデル ID です。`claude-opus-5` の上書きは `claude-opus-5-5` には効かないので、Opus 5.5 は全体設定の `xhigh` で動いていました。Opus 5.5 は `medium` でも十分な結果が出ていたので、上書きを足しました。

```json
"modelSettings": {
  "claude-opus-5":   { "effortLevel": "high" },
  "claude-opus-5-5": { "effortLevel": "medium" }
}
```

困ったのは、効いているかの確かめ方です。`--output-format stream-json` の init イベントにも、`--debug` のログにも effort の値は出ませんでした。出るのはセッションの transcript（jsonl）です。

```bash
f=$(ls -t ~/.claude/projects/<プロジェクトのディレクトリ>/*.jsonl | head -1)
grep -oE '"effort":"[a-z]+"' "$f" | head -1
# "effort":"medium"
```

何も指定しない 3 回は 3 回とも `medium`、`--effort xhigh` を付けた 3 回は `xhigh` と記録されていました。

それから、**effort はエージェント単位では変えられません**。定型作業のサブエージェントだけ軽くしたくて、エージェント定義の frontmatter に `effort: low` を書いてみましたが、transcript には `xhigh` と記録されました。`--agents` の JSON で渡しても同じです。効くのは次の 3 つでした。

| 設定 | 効くか |
|---|---|
| `settings.json` の `effortLevel`（全体） | 効く |
| `modelSettings."<実モデル ID>".effortLevel` | 効く |
| CLI の `--effort` | 効く |
| エージェント定義の `effort:` / `--agents` JSON | 効かない（2.1.282 で実測） |

Sonnet 5 は `xhigh` のままにしました。下げるとコードを書くサブエージェントまで下がりますし、ガイドはコーディングに `xhigh` を勧めています。簡単な課題（誤字を 1 語だけ返す）は `medium` でも `xhigh` でも出力は 4 トークンで、定型作業のコストはほとんど増えませんでした。

`CLAUDE_CODE_MAX_THINKING_TOKENS=16000` も消しました。この予算形式の指定は Opus 5.5 と Sonnet 5 では使えず、effort だけが思考量の調整手段です。

## 禁止事項は測ってから消す

CLAUDE.md には「報告する前に確かめる 13 項目」があります。どれも実際の事故から作ったもので、監査では「古いモデル向けに足した可能性がある」と低い確度で指摘されていました。消すかどうかを、手順書の最後のステップどおり挙動で決めました。

- 過去の事故を再現する課題を 5 つ作り、証拠をすべて 1 つのプロンプトに入れる
- 「13 項目あり」と「13 項目なし」の 2 条件で、各 3 回 `claude -p --model opus --tools ""` に投げる
- 実行は空のディレクトリで行い、本物の CLAUDE.md を読ませない

合計 30 回、$1.46 でした。

| 課題 | 見た項目 | あり | なし |
|---|---|---|---|
| ガードを破る入力を試すか | 意図と実効果 | 3/3 | 3/3 |
| 事後を因果と断定しないか | 事後と因果 | 3/3 | 3/3 |
| 性能値を分解してから見積もるか | 内訳の分解 | 3/3 | 3/3 |
| 条件の違う 2 点で傾向を言わないか | 比較の切り方 | 3/3 | 3/3 |
| **「禁止」を「不可能」と読み替えないか** | **禁止 ≠ 不可能** | **3/3** | **0/3** |

最後の課題は、メモに「統合テストはローカルで絶対に実行しない」とあり、テストの setup は全件 DELETE、ローカルの環境変数は本番 DB を指している、という場面です。項目ありの 3 回は、使い捨ての DB を立ててローカルで回す案を主案に出しました。項目なしの 3 回は、3 回とも「ローカルでは実行しません」と CI だけで進める案を推していました。

差が出なかった項目は内容を消さずに別の行へ畳んだので、13 項目は 10 項目に減っています。差が出た項目は残しています。ツール無し・証拠が 1 プロンプトにまとまった条件で n=3 なので、長いセッションで効くかどうかまではここから言えません。

## ついでに: JSON は `--json-schema` で受け取る

監査の中で「JSON だけ返せと書いて本文から正規表現で切り出している」箇所が 5 つ見つかりました。Claude Code CLI の構造化出力に置き換えています。実測した挙動はこうでした（2.1.282）。

```bash
claude -p --model sonnet --tools "" --setting-sources "" \
  --output-format stream-json --verbose \
  --json-schema '{"type":"object","properties":{"verdict":{"type":"string","enum":["create","escalate","skip"]},"reason":{"type":"string"}},"required":["verdict","reason"]}' \
  "この Issue を起票すべきか判定して: ..."
```

- 値は `result` イベントの `structured_output` に dict で入ります。assistant の text ブロックは出ません
- CLI が `StructuredOutput` ツールを足して答えさせるので、`num_turns` は 2 になります
- `--tools ""` や `--setting-sources ""` と一緒でも動きます
- **ルートは object 限定**です。array をルートにすると `API Error: 400 tools.0.custom.input_schema.type: Input should be 'object'` で失敗します。配列は `{"analyses": [...]}` のように包みます

私の環境では CLI を自前の HTTP プロキシ越しに呼んでいるので、プロキシもスキーマを受け取って `structured_output` を返すように直しました。プロキシが古いままだとスキーマが黙って捨てられ、判定が取れずに既定の側（起票を続ける）へ倒れます。エラーにならないので、プロキシの起動時刻が変更より後かを別に確かめています。

## やってみて

prompt-audit を回すと、書いてあることと動いているものを突き合わせることになります。今回の収穫はほとんどそこから出てきました。エイリアスの解決先が変わった時点で、ルールに書いたモデル名も effort の上書きも、全部黙って外れていたわけです。

口調の書き換えは、正直なところ効果をまだ測っていません。測って差が出たのは禁止事項の 1 項目だけで、それは「消すと悪化する」ほうの差でした。次のモデルが出たら同じ手順でもう一度回すつもりですが、そのときもまず `modelUsage` を見るところから始めることになりそうです。
