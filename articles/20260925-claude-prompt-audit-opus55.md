> **TL;DR**
> - Claude Code 同梱の `/claude-api prompt-audit` で、CLAUDE.md やプロンプトの古い書き方を洗い出せる
> - 自前のエージェントに当てたら、言い回しより「書いてあることと実物のずれ」がぞろぞろ出た
> - `opus` がいつの間にか Opus 5.5 になっていて、effort 設定も効かず重い `xhigh` のままだった
> - effort が効いているかは起動ログに出ない。セッション記録を見るしかない
> - 指示を消すなら、消した版と挙動を比べてから。1 つは消すと明確に悪化した

---

X で「`/claude-api prompt-audit` と打てば、skills・CLAUDE.md・プロンプトを Opus 5.5 の公式ガイドで書き直してくれる」という投稿が流れてきた。

Raspberry Pi 5 で自律エージェントを動かしていて、Claude は Claude Code の CLI（`claude -p`）経由で呼んでいる。ルールファイル、エージェント定義、実行時に渡すプロンプトは数か月分積み上がっていて、古いモデル向けに書いた言い回しがあちこちに残っている自覚はあった。書き直してくれるなら助かる。とりあえず当ててみた。

5 分では終わらなかった。サブエージェントに分担させて、反映と確認まで含めると数時間仕事。ただ、削れた量はかなりのもの。

## え、もう Opus 5.5 だったの

監査の前に「どのモデル向けに直すか」を決める必要がある。うちのルールには「既定は Opus 5」と書いてあるので、そのつもりで念のため `opus` の解決先を見た。

```bash
for m in opus sonnet; do
  claude -p --model $m --tools "" --output-format json "ok とだけ返して" \
    | python3 -c "import json,sys;print('$m ->', list(json.load(sys.stdin)['modelUsage']))"
done
# opus -> ['claude-opus-5-5']
# sonnet -> ['claude-sonnet-5']
```

とっくに Opus 5.5 だった。`opus` のようなエイリアスで指定していると、モデルだけが勝手に新しくなる。ルールもプロンプトも Opus 5 のつもりで書いたまま、実際は別のモデルが読んでいたことになる。

API の破壊的変更も一応確認した。Opus 5.5 では thinking を切る指定や `tool_choice` の強制が 400 になる。うちは Messages API を直接叩いていないので該当 0 件。見るのはプロンプトの中身だけで済んだ。

## prompt-audit は何をしてくれるか

`/claude-api prompt-audit` を打つと、スキルに入っている手順書（`shared/prompt-audit.md`）を読んで、その通りに動く。

1. 対象範囲と対象モデルを決める（聞き返さず、前提として報告に書く）
2. プロンプトとして効いているものを棚卸しする（system prompt、ツール定義、SKILL.md、CLAUDE.md、リクエストを組み立てるコード）
3. `git blame` で来歴を見る（その一文は、どのモデルのときに、どの事故を防ぐために足したのか）
4. 古いモデル向けの書き方のパターン表と照合する（強すぎる口調、今は API 機能で代わりがある工夫、細かすぎる手順など）
5. 指摘（`file:line`・理由・確度）と修正案の diff を出す
6. 消した指示が本当に不要だったか、挙動で確かめる

意外だったのは 6 番まであること。「削除は仮説であって結論ではない」と書いてあって、「消してはいけないもの」の一覧まで付いている。何でも消す道具ではなかったので、安心して任せられた。

量が多かったので 4 つに分けてサブエージェントに回し、確度が中以上の指摘だけを反映した。

| 対象 | 指摘 | 反映 |
|---|---|---|
| CLAUDE.md とルールファイル（6） | 21 | 10 |
| エージェント定義（6）と SKILL.md（10） | 23 | 9 |
| 実行時に `claude -p` へ渡すプロンプト（コード内） | 13 | 4 |
| 参照用のドキュメント（38） | 50 | 40 |

## 出てきたのは、言い回しより「ずれ」

古い口調を直す話だと思っていたら、数でも中身でも上だったのは、書いてあることと実物が食い違っている箇所だった。

- **4 月から一度も読まれていなかったルール**。ルールファイルには「このファイルを触ったら読み込む」という条件（`paths:`）を書ける。その条件が、4 月のリファクタで消えたファイルを指したままだった。一番読ませたい場面で、一度もロードされていなかったことになる。地味にショック
- **「除去済み」のはずの課金 API キー**。ルールには「課金経路は全ルートから外した」とあるのに、予備として 1 つのルートに残っていた。ログが残っている期間で成功 0 回・失敗 144 回。お金は出ていなかったが、毎晩失敗するだけの予備になっていた
- **書き写した「現在地」**。スキルが進捗ファイルの内容をコピーして持っていて、本体と食い違っていた。コピーは消して、本体を見に行く形にした
- **自分を待ち続けるループ**。`until ! pgrep -f "tidy-imports"` は、実行中の bash のコマンド全文（このパターン自体を含む）にも一致する。つまり永遠に終わらない

どれも grep と設定ファイルで実物と照合すれば見つかる。書き方の問題ではないので、モデルが賢くなっても直らない。

口調のほうも直した。実行時プロンプトにあった「必ずツールを使え」「推測で答えるな」系の強い指示は、何を根拠にするかと、その理由を書いた普通の文にしてある。

## effort（思考量）で一番ハマった

effort は、モデルがどれだけ考えてから答えるかの設定で、`low` / `medium` / `high` / `xhigh` / `max` の 5 段階。Opus 5.5 の既定は `medium`。Opus 5 の既定の `high` より一段下だが、同じ段階でも Opus 5 より多く考える、とガイドにある。

手元の `~/.claude/settings.json` はこうだった。

```json
{
  "effortLevel": "xhigh",
  "modelSettings": {
    "claude-opus-5": { "effortLevel": "high" }
  }
}
```

全体は `xhigh`、Opus だけ `high` に下げる、というつもりの設定。ところが `modelSettings` のキーは実際のモデル ID なので、`claude-opus-5` の行は Opus 5.5（`claude-opus-5-5`）には効かない。Opus 5.5 は上から 2 番目に重い `xhigh` で動いていた。Opus 5.5 は `medium` で十分な結果が出ていたので、1 行足した。

```json
"modelSettings": {
  "claude-opus-5":   { "effortLevel": "high" },
  "claude-opus-5-5": { "effortLevel": "medium" }
}
```

ここからが長かった。**効いているかをどこで確かめるのか分からない**。`--output-format stream-json` の最初のイベントを見ても、`--debug` のログを grep しても、effort の値が出てこない。

出力の量で推し量ろうともした。重めの計算問題を effort 別に投げたら、300 秒を超えて時間切れ。簡単な問題に変えたら、今度はどの effort でも出力 4 トークンで差が出ない。これはこれで「簡単な作業は effort を上げても高くならない」という収穫ではあったけど、確認にはならなかった。

最後に見つけたのが、セッションの記録（`~/.claude/projects/` の下にセッションごとに残る jsonl）。ここにだけ effort が書いてあった。

```bash
f=$(ls -t ~/.claude/projects/<プロジェクトのディレクトリ>/*.jsonl | head -1)
grep -oE '"effort":"[a-z]+"' "$f" | head -1
# "effort":"medium"
```

何も指定しない 3 回は全部 `medium`、`--effort xhigh` を付けた 3 回は `xhigh`。やっと確認できた。

ついでに、定型作業のサブエージェントだけ effort を下げられないか試した。エージェント定義の frontmatter に `effort: low` を書いても、記録は `xhigh`。`--agents` の JSON で渡しても `xhigh`。**effort はエージェント単位では変えられない**。効いたのはこの 3 つだけ。

| 設定 | 効くか |
|---|---|
| `settings.json` の `effortLevel`（全体） | 効く |
| `modelSettings."<実モデル ID>".effortLevel` | 効く |
| CLI の `--effort` | 効く |
| エージェント定義の `effort:` / `--agents` JSON | 効かない（Claude Code 2.1.282 で確認） |

Sonnet 5 は `xhigh` のままにした。下げるとコードを書くサブエージェントまで下がるし、ガイドもコーディングには `xhigh` を勧めている。さっきの 4 トークンの件のとおり、簡単な作業ならコストはほとんど増えない。

`CLAUDE_CODE_MAX_THINKING_TOKENS=16000` も消した。思考の上限をトークン数で決める古い方式で、Opus 5.5 と Sonnet 5 では効かない。

## 指示を消す前に、消した版と比べた

CLAUDE.md に「報告する前に確かめる 13 項目」を置いている。どれも実際にやらかした事故から作ったもので、監査では「古いモデル向けに足しただけかもしれない」と低い確度で指摘された。

消すかどうかは、手順書の 6 番どおり挙動で決めることにした。やり方はこう。

- 過去の事故をそのまま再現した課題を 5 つ作る。判断に要る情報は全部 1 つのプロンプトに入れる
- 「13 項目あり」と「13 項目なし」の 2 通りで、それぞれ 3 回ずつ `claude -p --model opus --tools ""` に解かせる
- 本物の CLAUDE.md を読ませないよう、空のディレクトリで実行する

合計 30 回で $1.46。

| 課題（事故の再現） | あり | なし |
|---|---|---|
| 書いた認証ガードを、破る入力で試そうとするか | 3/3 | 3/3 |
| 「直したら治った」を因果と決めつけないか | 3/3 | 3/3 |
| 所要時間を内訳に分けてから見積もるか | 3/3 | 3/3 |
| 条件の違う 2 つの数字で「増えた」と言わないか | 3/3 | 3/3 |
| **「禁止」を「不可能」と読み替えないか** | **3/3** | **0/3** |

4 つ目までは、13 項目があってもなくても全部正解。今のモデルなら書かなくてもできる、ということ。

差が出たのは最後の 1 つ。設定はこう。メモに「統合テストはローカルで絶対に実行しない」とあり、テストの準備処理はテーブルを全件削除する。しかもローカルの環境変数は本番 DB を指している。

項目ありの 3 回は、「禁止の理由は本番 DB を消すことだから、使い捨ての DB を立てればローカルで回せる」という案を主案に出した。項目なしの 3 回は、そろってローカル実行を断って、CI だけで進める案。禁止を「できない」と受け取って止まってしまう。

差が出なかった項目は中身を消さずに別の行へまとめ、13 項目を 10 項目にした。差が出た項目はそのまま残してある。どの課題もツール無し、3 回ずつなので、長い作業の中でも同じ差が出るかまでは分からない。

## ついでに: JSON は `--json-schema` で受け取る

監査の途中で、「JSON だけ返して」とプロンプトに書いて、返ってきた文章から正規表現で JSON を切り出している箇所が 5 つ見つかった。Claude Code CLI には、型を決めて受け取る `--json-schema` がある。

```bash
claude -p --model sonnet --tools "" --setting-sources "" \
  --output-format stream-json --verbose \
  --json-schema '{"type":"object","properties":{"verdict":{"type":"string","enum":["create","escalate","skip"]},"reason":{"type":"string"}},"required":["verdict","reason"]}' \
  "この Issue を起票すべきか判定して: ..."
```

実際に動かして分かったこと（Claude Code 2.1.282）:

- 結果は最後の `result` イベントの `structured_output` に dict で入る。普通の文章（text）は返ってこない
- CLI が内部で `StructuredOutput` というツールを足して答えさせるので、やり取りは 2 往復になる
- ツールなし（`--tools ""`）、設定なし（`--setting-sources ""`）でも使える
- **一番上は object でないとダメ**。配列を一番上にすると `API Error: 400 tools.0.custom.input_schema.type: Input should be 'object'` で落ちた。配列は `{"analyses": [...]}` のように包む

うちは CLI を自前の HTTP プロキシ越しに呼んでいるので、プロキシもスキーマを受け取って結果を返すように直した。ここで怖いのは、プロキシを再起動し忘れた場合。古いプロキシはスキーマを黙って捨てるので、判定が取れず、既定の側（Issue を起票する）に倒れる。エラーにならないから気づけない。プロキシの起動時刻が変更より後かは、別で確かめるようにしている。

## 自分の環境で確かめるなら

- `claude -p --model opus --output-format json` の `modelUsage` で、エイリアスが今どのモデルか
- `~/.claude/settings.json` の `modelSettings` のキーが、今のモデル ID になっているか
- effort が思った値か。セッション記録の jsonl を `"effort":` で grep
- ルールファイルの `paths:` が、今も存在するファイルを指しているか

## やってみて

prompt-audit を回すと、書いてあることと動いているものを突き合わせることになる。今回の収穫はほとんどそっちから出た。エイリアスの先が変わった時点で、ルールに書いたモデル名も effort の上書きも、全部黙って外れていたわけで、正直これは audit を回さなければ気づかなかった。次のモデルが出たらまた回すつもり。たぶんまた `modelUsage` を見るところから始まる。
